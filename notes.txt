PROJECT PURPOSE

Plumville is a Minecraft Bedrock transportation, navigation, construction, and planning project.

The world normally has no more than approximately four active players. The project is not intended to simulate real-world passenger volume, scheduling, station capacity, or service frequency. Its purpose is to make travel, navigation, planning, and collaborative construction around the Minecraft world easier.

The A-Z metro line naming system should remain.

Existing station names, line names, coordinates, path geometry, and visible behavior must not be changed during cleanup unless a task explicitly requires it.

MODERN MINECRAFT CONTROL PANEL DESIGN

The shared UI direction is Modern Minecraft Control Panel, abbreviated MMCP.

The intent is a sleek modern interface with recognizable Minecraft influence, not a novelty texture pack applied to every surface.

FOUNDATION

- Keep a near-black and charcoal dark-mode foundation.
- Let the terrain and metro line colors provide most strong color.
- Use crisp rectangular geometry and very small corner radii.
- Use subtle inset and raised borders inspired by Minecraft buttons and inventory slots.
- Use texture sparingly so the UI does not compete with the terrain.
- Avoid excessive gradients, pill-shaped controls, and generic rounded app styling.
- Use consistent spacing based on a small grid such as 4 px or 8 px.
- Use clear hover, focus, pressed, selected, disabled, success, warning, and danger states.

COLOR LANGUAGE

- Emerald-like green for success and completion.
- Torch or gold tones for warnings and important landmarks.
- Redstone-like red for errors and destructive actions.
- Diamond-blue for selection and active focus.
- Metro line colors for line identity.
- Purple and gold for Mt. Phosphagos landmark treatment.

TYPOGRAPHY

- Use clean modern body typography for readability.
- Reserve pixel-inspired typography for headings, short labels, coordinates, and decorative accents.
- Do not use a pixel font for long route instructions or dense forms.
- Keep station names readable at all supported display sizes.

ICONS

- Prefer simple block/pixel-inspired icons.
- Keep icon meaning obvious without requiring Minecraft knowledge.
- Use a home glyph for Mt. Phosphagos.
- Use consistent icon weights and sizing across desktop and web.


MAP SYMBOL SYSTEM

CIRCULAR METRO-LINE MARKERS

Circle means metro line.

Each line circle should have:

- Configured line color as the fill
- Bold centered line letter
- Automatic black or white text for contrast
- Thin contrasting outline
- Consistent screen-space size
- Accessible labels in the web interface
- Upright lettering regardless of line direction

Use line circles in:

- Line legends
- Line visibility controls
- Station details
- Route instructions
- Terminal markers
- Junction/interchange markers
- Major hub markers
- Construction views
- Selected-line information

STATION DIAMONDS

Diamond means station/place.

Ordinary station:

- Small diamond
- Neutral center or strong contrasting outline
- Visible over every metro line color
- Slightly larger and clearer than the current station points

Junction:

- Larger diamond
- Double outline or inner diamond
- Higher label priority
- Nearby cluster or row of applicable line circles

Terminal:

- Station diamond
- Adjacent circle for the terminating line
- Slightly heavier station outline if useful

Selected or searched station:

- Strong focus ring
- Higher label priority
- Remains visible regardless of normal semantic-zoom suppression

MT. PHOSPHAGOS

Mt. Phosphagos is the home landmark and receives unique permanent treatment.

- Larger station diamond
- Gold outer outline
- Home glyph inside
- Purple line remains visible around it
- Permanent high-priority label at normal zoom levels
- Gold accent repeated in station details and relevant route results
- Landmark outranks ordinary station-label collision rules

Purple and gold should make it feel royal without creating an unrelated symbol system.

STATION ABBREVIATIONS

DATA MODEL

Store the abbreviation in each station record:

{
  "var": "P_ABCDE",
  "lbl": "Blackport",
  "abbr": "BKP",
  "x": 294,
  "y": 390
}

Unnamed stations may omit abbr until they are named.

RULES

- Default expectation is all-cap abbreviations.
- Slimin is SLM.
- Typical length is 2 to 5 characters.
- Letters and numbers may be allowed.
- Do not silently generate and save an abbreviation without user review.
- Do not silently overwrite a user-entered abbreviation.
- Warn about duplicates.
- Duplicate abbreviations may be allowed only after explicit confirmation.
- Search should match full name, abbreviation, and existing station code/var where applicable.
- Full names remain the preferred close-zoom label.
- Abbreviations are a fallback for crowded views.
- Abbreviations should appear in station details and editing UI.

NAMING AND EDITING UI

When naming a station, include:

Station name
[                         ]

Abbreviation
[     ]

Behavior:

- Suggest an abbreviation from the name.
- Keep the suggestion editable.
- Never overwrite an existing user-entered abbreviation.
- Show a duplicate warning.
- Show a live map-label preview.
- Encourage an abbreviation when replacing a placeholder name.
- Save name and abbreviation together.
- Preserve abbreviation when line membership changes.


ROUTE AUTO-FIT

Both desktop and web should automatically fit the complete route after directions are calculated.

REQUIREMENTS

- Include every route segment and both endpoints.
- Add comfortable map padding.
- Account for the desktop sidebar.
- Account for the desktop station inspector if open.
- Account for the mobile bottom sheet.
- Avoid zooming absurdly close for very short routes.
- Preserve the highlighted route if the user pans away.
- Add a persistent Fit Route action.
- Swapping endpoints should recalculate and refit.
- Opening a shared web route should fit it automatically.
- Clearing a route should not unexpectedly reset the map unless explicitly requested.


WORLDGEN COMPLETION BEHAVIOR

World-generation controls should only appear when additional map generation is useful.

WHEN COMPLETION IS BELOW 100%

- Show generation controls in the World mode.
- Show clear current completion and active status.
- Allow supported generation and render operations.
- Prevent overlapping incompatible jobs.

WHEN COMPLETION REACHES 100%

- Finish or cancel pending work safely.
- Stop the generator/loader cleanly.
- Disable further Auto Fill work.
- Hide generation controls from normal UI.
- Show a compact World map complete status.
- Keep terrain display controls.
- Keep useful export and validation controls.
- Keep technical information available in Advanced if needed.

CONTROLS MAY REAPPEAR IF

- Render bounds change.
- Completion falls below 100%.
- Cache invalidation makes completion uncertain.
- The render is missing or invalid.
- A supported new map mode introduces incomplete space.

NONNEGOTIABLE REFACTOR RULES

The goal is to clean up and reorganize the project without changing functionality unintentionally.

Before moving, consolidating, or deleting code:

- Trace all callers.
- Account for runtime patching and dynamic behavior.
- Add regression tests for the behavior being moved.
- Establish baseline behavior.
- Move one tested slice at a time.
- Keep temporary re-export or compatibility wrappers.
- Confirm all preserved entry points still work.
- Do not combine broad structural cleanup with unrelated feature work.
- Do not delete compatibility files until callers have been removed and tests prove they are unnecessary.
- Do not delete a file merely because a normal text search does not show an import.

After each refactor slice:

- Run focused tests.
- Run the full Python suite.
- Run npm test.
- Run git diff --check.
- Record manual UI checks still required.

WORLDGEN RULES

- Do not optimize by guessing.
- Preserve all valid generation modes.
- Keep target planning deterministic and testable.
- Use atomic writes.
- Preserve recoverable progress after crashes.
- Avoid reprocessing unchanged data.
- Avoid unnecessary server restarts.
- Hide generation UI when no work remains.
- Avoid rewriting the complete image when a smaller update is possible.
- Consider tiled rendering only after profiling proves image rewriting is a bottleneck.
- Do not add parallel processing until measurements show it will help.
- Keep diagnostics out of normal UI unless an error occurs.

DESKTOP RENDERING RULES

Potential measured improvements:

- Avoid full redraws for small edits.
- Cache transformed geometry.
- Cache line/segment bounds.
- Precompute hit-test indexes.
- Cache label placement by zoom bucket and viewport.
- Separate static and interaction overlays.
- Use a quick interaction draw followed by one full redraw.
- Avoid rereading or recreating large images unnecessarily.

WEB RENDERING RULES

Potential measured improvements:

- Cache label placement by zoom bucket and viewport.
- Cache transformed geometry.
- Avoid drawing off-screen objects.
- Reduce labels and markers at distant zoom.
- Separate static and dynamic canvas layers.
- Keep terrain sharp at block-level zoom.
- Avoid rerendering the full map for bottom-sheet-only changes.
