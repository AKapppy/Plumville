<details>
<summary>[info] PROJECT PURPOSE</summary>


Plumville is a Minecraft Bedrock world transportation and planning project.

The project currently has two distinct user-facing applications:

1. Desktop application
   - Private authoring and administration tool.
   - Used by me on my computer.
   - Has full editing access.
   - May access private local data, world files, caches, diagnostics, Docker tools, rendering tools, construction records, and other backend systems.

2. Web application
   - Public, read-only visitor and helper guide.
   - Hosted from docs/ through GitHub Pages.
   - Used to view the map, search for locations, find directions, copy coordinates, understand which routes are usable, and see selected construction information.
   - Must not expose private desktop data or provide editing controls.

The world normally has no more than approximately four active players. This is not intended to model real-world transit capacity, passenger volume, scheduling, or station throughput. The goal is practical navigation around a large Minecraft world.

The A-Z line naming system should remain. Line names and existing station names should not be changed during structural or performance work unless explicitly requested.

</details>

<details>
<summary>[ ] ZOOMING AND PANNING</summary>


Desktop and web interaction should feel smooth even when the world map is large.

Potential improvements to evaluate through profiling:

- Coalesce repeated movement and wheel events.
- Use requestAnimationFrame in the browser.
- Permit only one pending browser redraw.
- Use a fast interaction render while moving.
- Trigger one higher-quality redraw after interaction stops.
- Cache label layouts by zoom range, viewport, and visible-line selection.
- Cache transformed route geometry.
- Cache line and segment bounds.
- Precompute hit-test indexes.
- Avoid recalculating every station and line during every pointer movement.
- Separate static and dynamic drawing layers.
- Draw the terrain, railway network, labels, and temporary overlays separately.
- Reduce visible detail at distant zoom levels.
- Avoid rendering off-screen objects.
- Preserve pixel-sharp terrain at block-level zoom.
- Do not re-read or recreate large images unnecessarily.

</details>

<details>
<summary>[ ] PATH ADDITION AND DETECTION</summary>


Path editing should update only affected records and visuals.

Potential improvements:

- Cache surface scans by world mode, bounds, and source-file revision.
- Reuse scans when seeds are added or removed.
- Recalculate only affected connected components when practical.
- Maintain indexed station, line, path-anchor, and endpoint lookups.
- Avoid rebuilding the entire network after one path edit.
- Avoid redrawing the entire map when only one path changed.
- Debounce disk writes and history snapshots.
- Validate the changed object immediately.
- Run full-network validation in the background or after save.
- Keep path detection in a worker thread or process.
- Provide responsive progress and cancellation.
- Preserve the existing path-preview workflow and functionality.

</details>

Worldgen and Auto Fill are major performance priorities.

Existing speedup and targeting patch modules likely contain useful working logic. Their behavior should be profiled and gradually integrated into proper worldgen modules rather than simply deleted.

Potential improvements:

- Move speed settings into configuration rather than mutating global constants.
- Keep the Bedrock process alive across safe batches when practical.
- Reduce unnecessary server restarts.
- Render only newly loaded or changed areas.
- Avoid rewriting the complete world PNG after every small update.
- Evaluate tiled render storage.
- Assemble a full public image only when exporting or publishing.
- Separate and time:
  - loading
  - decoding
  - classification
  - raster updates
  - PNG encoding
  - metadata writing
  - public copying
- Cache target-planning results using clear invalidation rules.
- Make target selection deterministic and testable.
- Use atomic writes.
- Preserve recoverable progress after crashes.
- Avoid reprocessing unchanged packet or chunk data.
- Use parallel CPU work only after profiling shows a real benefit.

     - width
     - height
     - world-map mode
     - renderer version
     - classification version
     - source revision

   - Fill tiny holes.
   - Preserve unknown pixels separately.
   - Never classify unrendered gaps as coastline.

   - area
   - bounding box
   - perimeter
   - compactness
   - major and minor axis
   - width distribution
   - endpoint count
   - boundary contact
   - known-versus-unknown border percentage

6. First classify:
   - sea/ocean
   - lake
   - pond
   - uncertain water

8. Classify enclosed broad water as lakes.

    - Broad water bodies become nodes.
    - Narrow corridors become edges.
