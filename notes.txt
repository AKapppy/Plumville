======================================================================
PROJECT PURPOSE
======================================================================

Plumville is a Minecraft Bedrock transportation, planning, navigation, and construction-tracking project.

It has three active areas:

1. Desktop application
   - Private authoring and administration tool.
   - Runs locally on macOS.
   - Has full editing access.
   - May use private local data, worldgen tools, diagnostics, and ignored runtime state.

2. Public web application
   - Read-only visitor/helper guide hosted from docs/ through GitHub Pages.
   - Used to view the map, search stations and coordinates, find directions, copy coordinates, understand route availability, and see selected construction information.
   - Must never expose private desktop data or editing controls.

3. Worldgen/backend
   - Local Minecraft Bedrock world generation, rendering, cache, and terrain-underlay tooling.
   - Uses Docker/LAN workflows.
   - Large generated files remain local and ignored.

The world normally has no more than about four active players. This is practical navigation and construction coordination, not real-world transit-capacity modeling.

Keep the A-Z line naming system. Do not rename existing lines or stations during structural, performance, or UI work unless explicitly requested.

======================================================================
AUTHORITATIVE WORKSPACE AND CODEX RULES
======================================================================

The local VS Code workspace is the authoritative complete development copy.

The GitHub repository is the authoritative tracked source, but intentionally excludes world files, generated worldgen data, local caches, runtime state, history snapshots, backups, node_modules, virtual environments, credentials, and other large/private files.

Whenever Codex works on Plumville:

- Inspect the actual local VS Code workspace before editing.
- Run git status first.
- Preserve all uncommitted, untracked, and gitignored work.
- Do not reset, checkout over, delete, regenerate, or overwrite unrelated work.
- Do not remove ignored files.
- Do not expose private local data in tracked/public locations.
- Do not commit, push, create branches, open pull requests, or change GitHub settings unless explicitly requested.
- Make focused, integrated changes.
- Do not create parallel replacement systems without a documented migration path.
- Prefer small, testable slices.
- Report every file created, moved, deleted, or modified.
- Report exact commands and test results.
- Identify manual-review items clearly.
- Keep code lines reasonably short where practical.
- Preserve current functionality, visuals, Docker behavior, and LAN behavior unless the task explicitly changes them.
- Never expose private paths, credentials, world files, caches, backups, diagnostics, local usernames, desktop-only state, or internal history data in docs/ or public exports.

The user can usually test web and mobile changes immediately. Desktop changes should be grouped into meaningful pull checkpoints because the user does not plan to pull after every small change.

DESIGN DIRECTION
======================================================================

MMCP = Modern Minecraft Control Panel.

Visual direction:
- Dark charcoal and near-black base
- Crisp rectangles and very small radii
- Subtle Minecraft-inspired borders/textures
- Modern readable body type
- Pixel-inspired headings, badges, coordinates, and short accents
- Metro colors as dominant identity colors
- Minimal gradients
- Strong contrast
- Compact but not cramped spacing

State colors:
- Emerald green = success/open/complete
- Gold = warning/landmark
- Redstone red = error/destructive
- Diamond blue = focus/selection
- Purple and gold = Mt. Phosphagos

Symbol grammar:
- Circle = line
- Diamond = station/place
- Larger/double-outline diamond = junction
- Terminal = station diamond plus line circle
- Mt. Phosphagos = larger gold-outlined home diamond
